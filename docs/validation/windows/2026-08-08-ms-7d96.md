# Windows Milestone 02 validation — 2026-08-08 — MS-7D96

## Result

- Observation milestone recommendation: `do not accept` (physical matrix incomplete)
- Suppression recommendation: `not evaluated; remains disabled`
- Summary: The native MSVC build, automated workspace gate, Windows capability probe, device and
  display enumeration, bounded observation runs, 20 start/stop cycles, sleep/wake, and one reboot
  succeeded as a standard user. The observed input remained conservatively `Unknown`, and the
  high-load run had no drops, untranslated packets, callback panics, ignored suppression requests,
  or capture discontinuities. Physical testing exposed fixes for variable-size keyboard packets,
  mixed-DPI geometry, public device-path disclosure, and boot-volatile Raw Input identities.
  Acceptance remains blocked on true receiver hot-plug and a second reboot to verify the new
  Container-ID-based identity scheme across boots.

## Defects and changes

### Raw Input interface path exposed as a device name

- Reproduction: `cargo run --quiet -p kvm-diagnostics -- devices`
- Expected: privacy-safe device labels plus application IDs and VID/PID metadata
- Actual: the complete Raw Input interface path was printed as `InputDevice.name`
- Safety impact: the path can contain a persistent device-instance identifier and should not be
  included in default diagnostics or evidence
- Fix: retain the path only as private identity metadata and publish `Raw Input keyboard` or
  `Raw Input mouse` as the user-facing name
- Files changed: `crates/kvm-windows/src/native.rs`
- Verification: `cargo test -p kvm-windows --all-targets`, post-fix `devices`, workspace tests,
  strict Clippy, and `git diff --check`

### Keyboard Raw Input packets rejected as truncated

- Reproduction: two targeted observation runs while typing normally in Notepad produced
  `summary_key=0`; the diagnostic split showed `native_keyboard_packets=0` while the aggregate
  untranslated count rose with every key press
- Expected: ordinary Raw Input keyboard make/break packets translate to canonical key events
- Actual: `read_raw_input` required every packet to be at least `size_of::<RAWINPUT>()`, even
  though Windows keyboard packets are smaller than the largest union variant on this ABI
- Safety impact: keyboard observation was entirely unavailable, while local typing correctly
  remained unaffected
- Fix: use zero-initialized, correctly aligned `RAWINPUT` storage and validate the returned packet
  against the active keyboard or mouse variant size; add redacted per-type packet counters
- Files changed: `crates/kvm-windows/src/native.rs`, `crates/kvm-windows/src/lib.rs`,
  `crates/kvm-windows/src/unsupported.rs`, and Windows-specific diagnostics output in
  `crates/kvm-diagnostics/src/main.rs`
- Verification: the targeted 15-second rerun produced 124 keyboard packets and 124 key events,
  with zero untranslated keyboard packets, drops, panics, suppression requests, or
  discontinuities; local Notepad typing behaved normally

### Mixed-DPI display enumeration returned inconsistent geometry

- Reproduction: `displays` reported `DISPLAY1` as logical 2560×1440 at scale 1.0 while
  `DISPLAY5` began at x=3840, creating an apparent 1280-unit gap despite the displays touching in
  Windows Settings; the operator confirmed `DISPLAY1` uses the recommended 150% scale
- Expected: coherent logical size, physical pixel bounds, scale, and physical adjacency
- Actual: the DPI-unaware thread received 96 DPI for both displays and a mixture of virtualized
  size and physical origin coordinates
- Safety impact: a future topology consumer could infer a nonexistent gap and fail to construct
  the intended cross-display boundary
- Fix: temporarily enter the per-monitor-v2 thread DPI context during enumeration, restore the
  previous context on every exit, query effective per-monitor DPI, retain physical virtual-screen
  bounds, and derive logical size from pixels divided by scale
- Files changed: `crates/kvm-windows/src/native.rs` and display presentation in
  `crates/kvm-diagnostics/src/main.rs`
- Verification: `DISPLAY1` now reports 3840×2160 physical, 2560×1440 logical, and scale 1.5;
  `DISPLAY5` reports 1920×1080 physical/logical at scale 1.0 and begins at the touching physical
  edge x=3840; 25 Windows tests and strict focused Clippy pass

### Raw Input IDs depended on boot-volatile interface instances

- Reproduction: compare shortened `devices` IDs before and after reboot
- Expected: the same physical receiver and HID collection retain an application ID across reboot,
  while separate devices and collections remain distinct
- Actual: the PID `C547` keyboard and pointer IDs changed because the Raw Input interface path's
  device-instance component changed; VID/PID alone cannot safely distinguish duplicate hardware
- Safety impact: saved device assignments could silently stop matching after reboot
- Fix: query the Windows device Container ID, combine it with a normalized HID collection
  descriptor that excludes only the boot-volatile instance, and use the same derivation for
  inventory and captured-event source IDs; retain conservative path/session fallbacks when the
  property is unavailable
- Files changed: `crates/kvm-windows/Cargo.toml`, `crates/kvm-windows/src/identity.rs`, and
  `crates/kvm-windows/src/native.rs`
- Verification: two consecutive post-fix inventories produced six distinct, exactly repeated IDs;
  unit tests prove that reboot-variant paths in one container converge while different containers
  and collections remain distinct. A second physical reboot remains pending.

## Conclusion

Windows observation-only capture is implemented and has passed its automated native build plus a
substantial physical smoke/lifecycle pass. These fixes are suitable for code review, but this
report does not yet recommend complete Milestone 02 Windows acceptance because true receiver
hot-plug and post-fix cross-reboot identity evidence remain incomplete. No result in this report
approves suppression, event routing, or an operational KVM.
